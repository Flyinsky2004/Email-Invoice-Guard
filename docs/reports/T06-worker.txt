## Behavior implemented

- `storage.Open(ctx, path, key)` validates a 32-byte key, opens a bounded SQLite pool with `foreign_keys=1`, `busy_timeout=5000`, WAL, `synchronous=NORMAL`, `_txlock=immediate` on every connection, applies embedded migrations atomically, and chmods the DB/WAL/SHM to 0600.
- In-memory stores use a random named URI per `Open` (`file:eig-<random>?mode=memory&cache=shared`) so independent Stores are isolated while one Store's pool shares its image.
- `Store.Transaction` passes a transaction-scoped `core.Repository`; returning an error rolls back; nested `Transaction` reuses the same `*sql.Tx` to avoid pool deadlocks.
- Full `core.Store` implementation: accounts/credentials/folders/cursors, emails/identities/attachments/parse failures, invoices/items/events/reminders, outbox/Telegram messages, assets, sessions/settings/status.
- Email identity: Microsoft immutable message ID; IMAP folder+UIDVALIDITY+UID; account-scoped uniqueness; conservative cross-folder fingerprint (account + Message-ID + sender + received time + body hash) with alias retention. Same Message-ID with a different body stays distinct.
- Invoice uniqueness `(account, provider, number)`; duplicates preserve paid/confirmed state and add all source-mail links; child IDs normalized; creation event recorded.
- `TransitionInvoice` CAS inside a transaction; paid metadata + event atomic; same-target idempotent; undo clears confirmation; JSON snapshot kept consistent with scalar state.
- `CreateReminder` only for pending invoices, validates calendar date, unique `(invoice_id, reminder_date)`, creates outbox in the same transaction (no orphan).
- Outbox: dedup never resets, exclusive lease claim with `attempts++`, expired SENDING → UNKNOWN and retried, complete/fail/skip synchronize linked reminders, bounded sanitized failure codes, per-part recording/retrieval.
- Assets: explicit identity (hostname or product ID) per provider/account; latest billing period updated as a pair; older invoice replay cannot overwrite period/model/OS/last invoice.
- Sessions: AES-256-GCM with purpose+token AAD, expiry enforced, `GetSession` non-consuming, `ConsumeSession` atomic one-time (replay fails).
- Credentials: AES-256-GCM with account AAD; plaintext token never stored; tamper/blob-swap fails authentication.
- Backup: absolute-path alias checks, rejects any existing target (symlink/hardlink included), creates the target with `O_CREATE|O_EXCL` 0600, `VACUUM INTO`, removes only its own file on failure.

## Unresolved issues / limitations

1. `RemoveAccount` cannot delete `oauth_sessions` rows because the frozen `SecureSession`/schema contracts carry no account association. Sessions are short-lived and one-time; credentials and cursors are erased as required.
2. WAL/SHM companions are chmodded to 0600 after Open/migrations. SQLite may recreate a companion with its default mode after a checkpoint during runtime; the main DB and all backups are enforced 0600. A stricter umask/OS-level control is outside this package.
3. `VACUUM INTO` is path-based. `O_EXCL` + `os.SameFile` defense prevents normal symlink/hardlink/relative aliases, but a local attacker able to replace the path between creation and VACUUM remains a TOCTOU risk; local filesystem trust is assumed.
4. In-memory stores use `MaxOpenConns(1)`. Callers must use the transaction-scoped repository inside `Transaction` (the frozen contract) to avoid self-deadlock; all internal list methods close rows before child queries.
5. Asset recency is keyed on `LastKnownServiceEnd`; observations without an end date never advance the stored period (they may only fill empty descriptive fields).
6. Only the RFCHOST provider row is seeded; `provider_rules` is intentionally empty (T04 owns parser rules).

## Security notes

- No plaintext credentials, session payloads, or tokens are persisted or logged.
- SQL is parameterized; the only dynamic SQL fragments are internal constant `WHERE` clauses.
- `RecordParseFailure` sanitizes and bounds provider/reason text.
- Backup never overwrites an existing file and cannot be redirected onto the live DB by relative/symlink/hardlink aliases.
- No real credentials or live external accounts were used.
