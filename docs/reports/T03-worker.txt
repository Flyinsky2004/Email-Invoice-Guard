## 2. Behavior implemented

- `mailproc.Normalize(core.NormalizedEmail) core.NormalizedEmail`: returns a deep-enough copy; fills `TextBody` from `HTMLBody` when text is absent; normalizes line endings/trailing whitespace without collapsing meaningful plain-text spacing; preserves full body length; extracts and merges only safe absolute `http`/`https` links (no userinfo/control chars); never renders HTML; never mutates input.
- `mailproc.HTMLToText(string) string`: removes comments, `<script>`, `<style>`, `<head>`; converts block tags to paragraph breaks; renders anchors as `text (url)` only for safe links; decodes entities; collapses HTML whitespace; preserves complete body.
- `mailproc.Classify(core.NormalizedEmail) core.Classification`: deterministic weighted keyword matching (subject weight 3, body weight 1), priority invoice/security/maintenance/promotion/other; strips `Fwd:`/`FW:`/`Re:` for matching but never filters forwarded mail.
- `syncengine.New(store, sources, parsers, linker, cfg, logger) *Engine`: exact frozen signature.
- `SyncAll`: lists accounts, skips disabled, runs enabled accounts with semaphore bound 4, joins sanitized errors; one failing account does not stop others.
- `SyncAccount`: keyed per-account lock shared by manual and periodic calls; lock acquisition is bounded (30s default, `engine.lockWait` overridable in tests) and honors context cancellation so shutdown is never blocked.
- `LastError`: persisted by re-reading the live account inside a transaction and updating only `LastError`/`UpdatedAt`; a stale in-flight snapshot can never re-enable a concurrently removed/disabled account. The write uses `context.WithoutCancel` plus a 5s deadline.
- Baseline: first sync persists `BaselineAt` cursor before any remote call; cutoff `BaselineAt-24h`; phases `historical` (no outbox, no invoice), `recent_initial`, `bootstrap_live`, then `incremental`.
- Folders: the catalog is refreshed on every sync. New folders are discovered and persisted; new non-Inbox folders default disabled; stored explicit enabled preferences (including a disabled Inbox) are never overwritten; disabled folders are never fetched. If discovery fails while folders are already known, the sync continues with the stored catalog and logs a sanitized diagnostic.
- Page processing: Normalize + Classify + parser outside transaction; before commit the live account is re-read and must still be enabled; transaction saves canonical email/identities, new valid/review invoice, assets via injected `linker.Reconcile(ctx, tx, invoice)`, exactly one delivery, and the cursor; rollback discards all page writes and leaves the pre-remote baseline cursor intact.
- Delivery kinds follow the T07 contract: `email` for ordinary mail, `invoice` for invoice-linked mail. A new email referencing an existing invoice still gets an `invoice` notification pointing at that invoice, while the invoice's payment state is untouched and no duplicate invoice row is created.
- Asset safety: only a newly created, sufficiently validated `PENDING_CONFIRMATION` invoice invokes `linker.Reconcile`. `REVIEW_REQUIRED` invoices never update asset last-invoice/service-period state automatically, but still receive an `invoice` notification and retain their original source email entry.
- Parser failure: diagnostic only; mail is still saved and delivered, cursor advances, reason bounded to 200 runes/control-stripped and persisted in `X-Parse-Failure` header plus `RecordParseFailure` with the canonical EmailID and vendor provider ID (`invoice.ProviderID`, e.g. `rfchost`) — never the provider message ID.
- Parser contract: an invoice returned together with a non-nil error is forced to `REVIEW_REQUIRED` with a bounded review reason; it is never defaulted to `PENDING_CONFIRMATION`.
- Canonical identity: `invoice.SourceEmailID` is set from the email returned by `SaveEmail` inside the transaction, so a storage-layer canonical ID is used.
- Duplicate handling: remote identity/fingerprint replay creates no second email/delivery; a new email referencing an existing invoice is still delivered while only one invoice row exists; existing paid state is preserved.
- UIDVALIDITY change: rebuilds that folder's baseline before processing, so old mail is stored historical and deduped rather than replayed.
- Baseline rebuild: an explicit `NextCursor.BaselineAt` change (Microsoft 410) or a UIDVALIDITY change starts a new baseline. The current page is classified against the new baseline and the new cursor is committed atomically with the page, never inheriting the old `BaselineComplete` flag; historical mail is not pushed.
- IMAP baseline safety: when only UIDVALIDITY changes, the rebuilt baseline is `now`; a retained non-zero `NextCursor.BaselineAt` from IMAP is treated as stale and never used. IMAP `BaselineAt` stays engine-managed across pages, and a failed page transaction leaves the old cursor intact.
- Damaged MIME safety: `X-Invoice-Guard-Decode-Error` is read case-insensitively. If a damaged body still yields an invoice, the invoice is forced to `REVIEW_REQUIRED`, a bounded parse failure is recorded with the vendor provider ID, and asset/reminder work is skipped. Ordinary mail carrying the same marker is still delivered in full.
- `Run`: periodic loop, re-reads `sync_interval_seconds` between passes, falls back to `cfg.SyncInterval`, then 60s; returns nil on context cancellation.

## 5. Unresolved issues / integration notes

- T08 stage B must inject the real `core.ParserRegistry` and `core.AssetLinker`; `nil` linker/parser is supported only for tests.
- Provider paging semantics (Graph delta links, IMAP UID snapshots) are delegated to `core.MailSource`; the engine consumes `SyncBatch` and never assumes a UID across folders.
- Folder discovery runs only when no stored folders exist (per SPEC “discover folders if absent”); folders added later are not auto-imported.
- Historical mail skips the parser entirely, so no invoice or parser diagnostic is produced for it (per “no formal active invoice”).
- For a hard parser error with no invoice, the vendor provider ID may be empty because the frozen `ParserRegistry` interface exposes no per-email vendor lookup; when a review invoice is returned, `invoice.ProviderID` is used.
- Review invoices receive an `invoice` delivery; a new email referencing an already-existing invoice also receives an `invoice` delivery without touching payment state.
- No live Microsoft/QQ/Telegram credentials or external accounts were used.
- Full `go test ./...` and E2E remain for T08 after sibling modules merge.

## 7. Security risks / limitations

- `HTMLToText` is regex-based, not a full HTML parser. It removes script/style/head/comment blocks, strips tags, decodes entities and never renders HTML; malformed/unterminated markup can leave text content but cannot execute or render.
- Only absolute `http`/`https` URLs without userinfo/control characters are retained; `javascript:`, `data:`, `mailto:`, relative and credential-bearing URLs are dropped.
- Provider errors are collapsed to bounded safe codes before returning or persisting; raw provider text is never included in joined errors or `LastError`.
- Parser diagnostics are bounded to 200 runes with control characters removed; no credentials, tokens or full bodies are logged (slog emits account/folder IDs and codes only).
- Deduplication uses remote identity plus a conservative sender/time/subject/body fingerprint; identical messages arriving in multiple folders collapse to one canonical email while aliases remain the storage layer’s responsibility.
- Delivery is one enqueue per new email; downstream outbox semantics remain at-least-once (T06/T07), never exactly-once.
- The engine performs no network calls inside the SQLite transaction; the injected linker participates in the caller’s transaction.
