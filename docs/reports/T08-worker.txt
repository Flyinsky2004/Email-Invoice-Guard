------------------------------------------------------------------
所有测试使用真实 storage + 真实 sync 引擎 + 真实 RFCHOST parser +
真实 lifecycle/reminder/telegram；外部依赖全部本地 mock，无真实账号或密钥。

A. TestTLSIMAPInvoiceLifecycle（TLS IMAP → 全链路）
   1. 真实 imap.Source 连接 imaptest 的 TLS IMAP 服务器（自签 CA，仅测试信任）。
   2. 真实 RFCHOST 账单邮件 → 一条 PENDING 账单 + 1 条 outbox。
   3. DeliverOnce → 恰好 1 条增强投递；断言账单号 143058、金额 6.84 USD、
      到期日 2026-10-24、可信商家 URL、原始邮件回调。
   4. Bot.Run 真实长轮询：
      - 回调 p:<id> → 只出现二次确认提示（含 pc:<id>），账单仍 PENDING；
      - 回调 pc:<id> → 账单 PAID_CONFIRMED，事件数 2（CREATED+PAID）。
   5. 创建当天 Tick 不产生提醒（即便 PENDING）。
   6. 回调 pu:<id> → 撤销回 PENDING。
   7. 次日本地日 Tick → 恰好 1 条唯一提醒；重复 Tick 仍为 1（持久唯一约束）。
   8. 投递失败重试：注入 1 次 sendMessage 失败 → 提醒 FAILED；再次 DeliverOnce
      → SENT（真实 claim/fail/retry 路径）。
   9. 关闭并重开 SQLite：游标 Value/BaselineComplete、账单状态、提醒状态均保留；
      再次同步不产生重复 outbox（游标恢复、重放幂等）。

B. TestMockGraphInvoiceLifecycle（mock Graph → 全链路）
   真实 microsoft.Source + 注入 HTTP client + mock Graph（well-known 文件夹、

   首次同步 → 账单 + 1 条投递；DeliverOnce → 1 条增强消息；
   第二次同步复用 deltaLink，不重复投递。

C. TestLongEmailDeliveredWithoutTruncation（超长全文）

七、集成问题 / 限制（需告知）
------------------------------------------------------------------
1. IMAP 自定义主机/域名无法从配置注入（真实限制，未改契约）
   - imap.Source 通过导出字段 AllowedHosts/AllowedDomains 限定 QQ 主机与域名，
     但 core.IMAPConfig 没有对应字段，app.Run 无法从环境变量配置它们。
   - 影响：生产组合仅支持默认 imap.qq.com 与 qq.com/foxmail.com 域名。
     若需支持其他 QQ 托管域名或自建 IMAP 主机，需要 Codex 评估是否扩展
     core.IMAPConfig（本 worker 未修改冻结契约）。
   - 默认 QQ 场景不受影响，E2E 通过显式设置导出字段验证了真实 TLS 路径。
2. E2E 提醒测试的时间接缝
   - reminder.Tick 用传入的 now 作为 outbox available_at；测试模拟“次日”后
     需先把 PENDING 投递的 available_at 调整为已到期，再走真实 DeliverOnce。
     已记录到 LESSONS.md，未改变生产逻辑。
3. Telegram 至少一次语义、外部消息不可原子回滚等限制保持文档所述。
4. Docker 镜像为本地 eig-t08-verify 标签；未推送、未覆盖其他标签。
