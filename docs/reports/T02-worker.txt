Behavior implemented
--------------------
imap.New(repo, cfg) *Source
  - core.MailSource.Type() == core.QQ.
  - Defaults: imap.qq.com:993, ServerName imap.qq.com, 30s timeout, batch 20.
  - Explicit allowlists: AllowedDomains (default qq.com/foxmail.com, subdomains
    such as vip.qq.com accepted) and AllowedHosts (default imap.qq.com). An
    arbitrary IMAP host is rejected before dialing.
  - TLS always verifies hostname and roots; InsecureSkipVerify is rejected.
  - Injectable Dial and TLSConfig for the fake TLS server tests.
  - A deadlineConn clamps every SetDeadline/SetReadDeadline/SetWriteDeadline to
    min(ctx deadline, now+cfg.Timeout), because go-imap installs its own 30s
    per-command deadlines. Silent TLS peers and silent IMAP greetings fail
    within the configured timeout.
  - Context cancellation closes the connection.

Source.Validate(ctx, address, authorizationCode)
  - Normalizes/validates the QQ-hosted address, rejects empty/control-character
    codes, performs a real TLS IMAP LOGIN with the third-party authorization
    code (never a QQ password), then LOGOUT. Nothing is persisted.
  - IMAP NO on LOGIN maps to core.ErrReauthorization; TLS/network failures stay
    distinct.

Source.ListFolders
  - LIST "" "*", skips \Noselect/\NonExistent, maps SPECIAL-USE roles
    (inbox/sent/drafts/trash/junk/archive/all/flagged/important) with a
    conservative name fallback, enables INBOX only.
  - Stable 32-hex folder IDs derived from account ID + mailbox name. Only
    INBOX is normalized case-insensitively (RFC 9051); every other mailbox
    keeps the server's original case, so "Foo" and "foo" remain distinct
    mailboxes with distinct IDs and UID state.

Source.Sync
  - SELECT snapshots UIDVALIDITY/UIDNEXT (STATUS fallback).
  - UIDVALIDITY change or new folder state restarts LastUID at 0.
  - Bounded UID range with 64-bit arithmetic (no uint32 overflow); HasMore is
    returned and the cursor advances only to the last UID actually consumed.
  - Phase 1 FETCH: UID, ENVELOPE, INTERNALDATE, BODYSTRUCTURE (extended).
  - Phase 2 FETCH per message: BODY.PEEK[HEADER], BODY.PEEK[part] and
    BODY.PEEK[part.MIME] for text/plain and text/html only.
  - joinMIMEPart ALWAYS prepends BODY[part.MIME]; body content is never used to
    infer headers (a body may legitimately begin with a Content-Type line).
  - If the server omits BODY[part.MIME], headers are synthesized from
    BODYSTRUCTURE (media type, charset, transfer encoding) so decoding remains
    correct instead of guessing from content.
  - decodeText reads text parts in full (no truncation). On message.Read or
    io.ReadAll failure it returns the original encoded text; if io.ReadAll
    produced a partial decoded prefix, both the prefix and the raw encoded
    text are preserved. The failure is marked with a bounded
    X-Invoice-Guard-Decode-Error header and a sanitized Warn log, so the cursor
    never commits a silently emptied part.
  - Attachments are metadata-only from BODYSTRUCTURE (filename, content type,
    encoded size); binary bodies are never downloaded. A missing BODYSTRUCTURE
    is an explicit error, never a BODY[] fallback.
  - No STORE/flag changes, so messages are never marked read.
  - A UID that vanishes between snapshot and body fetch is skipped safely; a
    fetch/connection error returns no cursor so the next pass retries.
  - ProviderMessageID = folderID:uidvalidity:uid (same UID in different folders
    is distinct); cross-folder fingerprint = sender + subject + sender time +
    Message-ID + decoded bodies; Historical/Phase derived from the cursor
    baseline (pipeline-owned baseline is preserved).

qq.NewOnboarding(repo, cfg, source) *Onboarding
  - Begin(actorID): 256-bit bearer token, only SHA-256 hash persisted in a
    SecureSession with purpose qq_setup and TTL (default 10m). PublicBaseURL
    must be absolute HTTPS (or empty for a relative path); validation happens
    before any session is stored.
  - ServeHTTP only accepts /setup/qq (and trailing slash).
  - Transport: direct r.TLS, or a RemoteAddr inside cfg.TrustedProxyCIDRs with
    X-Forwarded-Proto: https. Empty CIDR list trusts no proxy. Forged forwarded
    headers from untrusted peers are rejected. PublicBaseURL alone is never
    treated as proof of HTTPS.
  - GET validates the hashed token and renders the form; it never consumes the
    token and never echoes it.
  - POST requires application/x-www-form-urlencoded, bounds the body to 16 KiB,
    validates the session and address, performs the real IMAP validation, and
    only then consumes the token and persists the account+credential.
  - Persistence is one Store.Transaction when the repository implements
    core.Store (consume + upsert + SaveAccount + PutCredential); otherwise the
    sequential path is used. No network call happens inside the transaction.
  - Existing (provider, address) accounts are reused: owner mismatch returns
    ErrUnauthorized (HTTP 403), same owner re-enables the account, updates the
    credential, preserves CreatedAt and history, and avoids the
    UNIQUE(provider,address) violation.
  - Responses set Cache-Control: no-store, Pragma: no-cache,
    Referrer-Policy: no-referrer, X-Content-Type-Options: nosniff,
    X-Frame-Options: DENY and a restrictive CSP. Secrets are never echoed or
    logged; persist failures are logged without the underlying error value.

Tests
-----
75 tests total (53 imap, 22 qq), using a real in-process TLS IMAP server
(github.com/emersion/go-imap/v2/imapserver) and fake repositories that embed
core.Repository/core.Store. Coverage: imap 84.9%, qq 83.6%.

Covered scenarios include: default config; address/domain and host allowlists;
empty/control-character codes; invalid authorization code; untrusted TLS cert;
InsecureSkipVerify rejection; silent TLS peer; silent IMAP greeting; shorter
context deadline; folder roles and stable IDs; unicode MIME with
quoted-printable and base64; attachment metadata and no attachment section
download; UIDVALIDITY reset; same UID in different folders with equal
fingerprint; bounded batches without skipping; vanished UID; connection failure
without a cursor; auth failure; missing credential; provider mismatch; no STORE;
context cancellation; 9 MiB text not truncated; missing BODYSTRUCTURE; UID range
overflow; HTTPS/proxy trust matrix; GET no-consume; POST content-type/oversize;
invalid code stores nothing; atomic success; replay; concurrent replay; account
reuse; owner conflict with transaction rollback; malformed/expired session;
non-Store repository path; security headers.

Acceptance-rework regressions added:
  - Corrupted base64 text part: raw encoded content preserved, decode-failure
    header set, no silent empty.
  - Corrupted quoted-printable text part: content preserved (Go's QP reader is
    lenient and passes invalid escapes through).
  - Partial io.ReadAll: partial decoded prefix plus remaining raw text kept.
  - Plain part without BODY[part.MIME]: headers synthesized from BODYSTRUCTURE,
    full body preserved, no false decode-failure marker.
  - Body beginning with a Content-Type line: never mistaken for MIME headers;
    full body preserved.
  - joinMIMEPart always prepends headers.
  - LIST returns "Foo" and "foo" as distinct folders with distinct IDs; only
    INBOX is case-insensitive.

Security risks / limitations
----------------------------
- cfg.Timeout bounds the entire connection lifetime (min with the caller's ctx
  deadline). A very large batch or slow server needs a larger configured
  timeout; this is deliberate anti-hang behavior.
- The setup POST has no application-level rate limiting; deployment should add
  edge limits (T08).
- Reverse-proxy trust is opt-in only through TrustedProxyCIDRs; default empty
  means direct TLS is mandatory. Invalid CIDR entries fail closed.
- The authorization code is held in memory during validation and passed to the
  repository, which encrypts it per schema. It is never logged or echoed.
- On a text decode/read failure the raw encoded content is preserved and marked
  with X-Invoice-Guard-Decode-Error; downstream parsers should treat that
  header as a diagnostic and may still see encoded text. Attachment bytes are
  never fetched.
- On the non-Store repository path, the token is consumed before SaveAccount;
  a save failure after consumption loses that setup link. The Store path is
  atomic. Production storage implements core.Store.
- No real QQ account or credential was used; all IMAP integration tests use a
  local TLS server with a test CA.
