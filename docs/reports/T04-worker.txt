## Implemented behavior
- Registry rejects duplicate vendor/version with `core.ErrConflict`; invalid/nil metadata with `core.ErrInvalid`; `Parsers` returns an independent copy; unknown mail returns `core.ErrNoMatch`; a matched parser's invoice + error are returned together (non-fatal to pipeline).
- Match requires a conservative RFCHOST sender (`rfchost.com` or subdomain, display-name tolerant) plus at least two explicit invoice signals (number, amount due, due date, subtotal, credit, total, trusted invoice URL). Partial invoices are still matched so Parse can record review diagnostics.
- Parse prefers `TextBody`, falls back to `HTMLBody` via `golang.org/x/net/html` (no mailproc dependency); tolerates CRLF, blank lines, NBSP, table tags.
- Extracts number, generated date, due date, payment method, currency, amount due, subtotal, credit, total, explicit `Account Balance`, trusted URL.
- Payment method normalization only for explicit `Alipay+`; other values preserved.
- Items: any count; model/hostname, service period, OS, original price, unicode promo code (spaces/special chars), full discount type phrase (e.g. `Recurring Discount`), negative amount, integer basis points, final price. Discounts attach to their own item block.
- Mandatory: number, currency, due date, amount due. Invalid mandatory fields never produce `PENDING_CONFIRMATION`; missing number returns nil + `ErrReviewRequired`.
- Review triggers: missing total, item/subtotal sum mismatch, subtotal − credit ≠ amount due, total mismatch, percent inconsistency beyond ±1 minor unit, negative original price/amount due/subtotal/credit/total, positive discount amount, discount > 100%, unordered item dates, URL id ≠ invoice number, untrusted URL.
- Credit never fills `AccountBalance`; balance only from explicit `Account Balance`.
- Documented credit presentation variant accepted: when credit ≠ 0, `Total == SubTotal` is allowed while `AmountDue == SubTotal − Credit`.
- URL: exactly `https://my.rfchost.com/viewinvoice.php` with exactly one `id` query param equal to the invoice number; userinfo, port, fragment, redirect/extra query params rejected and URL left empty.
- No floating point anywhere; all money arithmetic is checked `int64` (overflow detected).

## Unresolved issues / limitations
- Parser has no repository dependency, so there is no `core.Repository`/`core.Store` fake to embed; the meaningful injected fake is `core.InvoiceParser` for registry behavior. Noted rather than adding a meaningless fake.
- Credit presentation variant (`Total == SubTotal` with non-zero credit) is accepted conservatively; if real RFCHOST semantics differ, tighten this rule.
- HTML conversion is intentionally simple (block → newline, cell → space); deeply nested layouts may need tuning.
- Invoice number pattern is `[A-Za-z0-9][A-Za-z0-9_-]*`; extend if RFCHOST emits other characters.
- No live vendor mail samples beyond the frozen fixture were available.

## Dependency requests
- None. Uses already-pinned `golang.org/x/net v0.62.0` (present in `go.mod`); no `go get`/`go mod tidy` run.

## Security risks / limitations
- Untrusted HTML is parsed with `x/net/html` and reduced to text; `script/style/head/title` are skipped.
- Invoice URL is restricted to the fixed HTTPS host/path with a single `id` param matching the invoice number; userinfo, non-443 ports, fragments, redirect/extra params are rejected and never emitted as clickable.
- Parser performs no network I/O and logs no bodies or credentials.
- No secrets in source or tests; the only userinfo string is the literal non-secret `user:pass`.
- Merchant recognition is descriptive, not proof of authenticity; the application never pays a vendor (architecture constraint).
