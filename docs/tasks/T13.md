Runtime composition in `internal/app/run.go`:
- Construct `manual.NewService(store, cfg, logger)`; `*storage.Store` satisfies `core.ManualReminderRepository`.
- Run the manual scheduler in its own goroutine with the same context as the invoice scheduler, and wait for it during graceful shutdown alongside the existing goroutines. A scheduler error must be surfaced through the existing error path, not silently dropped.
- Construct the bot with `telegram.NewWithManual(..., manualService, ...)`; keep `telegram.New` untouched.
- Startup order: storage open and migrate, then services, then bot and schedulers. No network or Telegram call before migrations complete.

Documentation: `README.md` gains a manual-reminder section (commands, wizard, daily summary, month-end clamping, timezone, confirmation semantics, that mail never marks a plan paid); `docs/setup/telegram.md` gains the manual commands and callback behavior plus the `MANUAL_*` variables.

End-to-end test in `tests/e2e/**` (mock Telegram HTTP, real SQLite, injected clock):
1. Create a plan through the manual service with a due date in the current month.
2. Tick at the plan-local reminder time; assert exactly one pending occurrence and one `manual` outbox delivery with dedup key `manual-reminder:<planID>:<localDate>`.
3. `DeliverOnce` against the mock Telegram; assert one summary message and `SENT` mirrored on the dispatch.
4. Confirm the occurrence; assert `PAID_CONFIRMED`, the event, and that a second tick the same day creates no duplicate summary.
5. Advance the clock to the next month, tick, and assert the next occurrence and a new summary.
6. Reopen the store (restart) and assert no duplicate occurrence or dispatch is produced and the paid state survives.
