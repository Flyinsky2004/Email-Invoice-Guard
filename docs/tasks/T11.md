### Recurrence matrix (feature spec §10)

| Case | Required behavior |
|---|---|
| `billing_day` 1–28 | due date is that day in every month |
| `billing_day` 29, 30, 31 in a short month | clamp to that month's last day (`last_day` policy); e.g. 31 → 2026-02-28, 31 → 2026-04-30, 29 → 2028-02-29 |
| Plan creation | `next_due_date` is the first billing date on or after the plan-local today; no occurrence is created for a past date |
| Tick before `reminder_time` in plan-local time | no occurrence or dispatch for that day |
| Tick at/after `reminder_time`, `next_due_date <= today` | create the pending occurrence for `next_due_date`, advance `next_due_date` one month (clamped), then consider the daily summary |
| Tick with `next_due_date > today` | no occurrence; a summary is still produced only if a pending occurrence is due on or before today |
| Catch-up | at most `cfg.Manual.MaxCatchUpMonths` months are materialized; an older `next_due_date` jumps forward to the first billing date on or after today instead of backfilling unbounded history |
| Repeated tick, same local day | no duplicate occurrence (`UNIQUE(plan_id, due_date)`) and no duplicate summary (`UNIQUE(plan_id, local_date, kind)`) |
| PAUSED plan | no new occurrence and no summary; existing pending occurrences remain visible |
| CANCELLED plan | no scheduling at all |
| Resume | `next_due_date` becomes the first billing date on or after today; missed periods are not backfilled |
| Plan-local timezone | every calendar decision uses the plan timezone, never the process default; DST does not shift the calendar date |
| One summary per plan per local day | a single `DAILY_SUMMARY` dispatch covers all occurrences due that day; `DailyRetry` only allows a later daily attempt, the dedup key still prevents duplicates |
| Restart | all scheduling state is persisted; no in-memory-only dedup, no replay of already-dispatched days |
| Mail | never marks a manual plan or occurrence paid; only `ConfirmOccurrence` does |

Deliverables:
- `recurrence.go` — pure calendar helpers: next billing date, month-end clamping, catch-up bound, plan-local date conversion. No I/O, exhaustively table-tested.
- `plan.go` — create/update/pause/resume/cancel with validation (non-empty title, billing day 1–31, loadable timezone, `HH:MM` reminder time, `last_day` policy, amount currency supported by `core.CurrencyDecimals`) and event writes.
- `occurrence.go` — occurrence creation, confirmation and revocation; confirmation is `PENDING_CONFIRMATION→PAID_CONFIRMED`, revocation is the reverse, both authorized, idempotent on same-target replay, and both write their event atomically through the repository call.
- `scheduler.go` — `Tick`/`Run` implementing the matrix; the daily summary is enqueued through `CreateDispatch` with `Kind: core.ManualDispatchDailySummary`, `DeliveryPayload.Kind: "manual"`, `ManualPlanID`, `ManualOccurrenceIDs`, and dedup key `manual-reminder:<planID>:<localDate>`.
- `service.go` — the `core.ManualReminderService` surface, read methods and `ListPlanMessages`/`Events`.
- Tests and fakes: a fake `core.ManualReminderRepository` records calls and enforces the documented `false` conditions; injected clock for every scheduling test.
